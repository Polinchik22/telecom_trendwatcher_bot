# Телеком-трендвотчер

Telegram-бот, который автоматически отслеживает новости телеком-отрасли
из нескольких источников на разных языках, размечает их по темам и
позволяет находить нужную информацию по хештегу или обычным вопросом на
естественном языке. Часть интеллектуальной работы — понимание смысла
запроса, разметка сложных статей, перевод, генерация ключевых слов для
новых тегов — выполняет локальная LLM (Ollama), без обращения к платным
облачным API.

## 1. Идея проекта

Инструмент, который:
1. Сам собирает статьи из выбранных источников (RSS-ленты, включая
   источники не на русском и не на английском)
2. Сам раскладывает их по темам (хештегам) — компании, технологии,
   регуляторика, M&A и так далее
3. По запросу показывает, что нового вышло по теме: краткое саммари,
   до 5 свежих статей, динамику упоминаемости
4. Понимает не только точные хештеги, но и вопросы своими словами
5. Позволяет любому пользователю добавить свой хештег диалогово —
   написал /addtag, бот спросил имя, LLM сама подобрала ключевые слова

## 2. Архитектура

```
RSS-источники (RU/EN/ZH и др.)
        │  (параллельно, с тайм-аутом 15 сек на источник)
        ▼
   crawler.py  ──────────────►  llm_client.py (перевод, LLM-теги,
        │                        генерация ключевых слов, дайджесты,
        │  (словарное тегирование:                понимание запроса)
        │   tags.py + custom_tags)     │
        ▼                              │
   articles.db (SQLite)  ◄─────────────┘
        │
        ▼
  hashtag_search.py (поиск, саммари, динамика, тренды)
        │
        ▼
    bot_v7.py  ◄──── llm_client.py (LLM понимает запрос, если словарь не справился)
        │
        ▼
     Telegram (ответ пользователю, с ретраями при сбоях сети)
```

Ключевое архитектурное решение с самого начала: **словарь — основной
механизм, LLM — дополнение**. Быстрое бесплатное словарное тегирование
покрывает большинство статей мгновенно; LLM подключается там, где
словарь бессилен — сложные формулировки, вопросы на естественном
языке, статьи на других языках, генерация ключевых слов для новых
тегов. Все обращения к LLM обёрнуты в защиту от сбоев: если Ollama
недоступна, соответствующая функция просто возвращает пустой результат
вместо падения бота.

## 3. Структура файлов

### Точка входа

**`bot_v7.py`** — главный файл (`python3 bot_v7.py`). Диспетчер команд
и сообщений Telegram, ничего не считает сам — вызывает функции из
остальных модулей.

Публичные команды (доступны любому):

| Команда | Что делает |
|---|---|
| `/start`, `/help` | приветствие и список функций |
| `/actual` | 3 самые обсуждаемые/быстрорастущие темы (см. п. 6) |
| `/tags` | список тем, по которым есть статьи |
| `/status` | сколько статей в базе, с тегами, разбивка по источникам |
| `/addtag` | добавить новый тег — диалогово: команда → бот просит имя → LLM сама подбирает ключевые слова |
| `#хештег` / текст без `/` | поиск по теме |

Административная команда:

| Команда | Кому доступна |
|---|---|
| `/collect` | только разработчику (проверка по Telegram user ID) — тяжёлая операция: сбор + перевод + LLM-теги + дайджесты, поэтапно отчитывается в чат |

Постоянная клавиатура (`ReplyKeyboardMarkup`) с кнопками `/actual`,
`/tags`, `/status`, `/addtag`, `/help` показывается под полем ввода —
не нужно помнить команды.

Диалоговое состояние для `/addtag` хранится в простом множестве в
памяти процесса (`pending_addtag_users`) — если человек вызвал команду
без аргументов, его следующее обычное сообщение перехватывается и
трактуется как имя тега, а не как обычный поисковый запрос.

Все ответы бота идут через `safe_reply()` — обёртку с 3 попытками
отправки: сеть до Telegram иногда обрывается (`ConnectTimeout`), без
ретраев такое сообщение просто терялось бы навсегда, даже если бот всё
честно посчитал. Дополнительно у HTTP-клиента увеличены тайм-ауты
подключения (30 сек вместо дефолтных) — бот терпеливее к нестабильной
сети.

### Сбор данных

**`sources.py`** — список источников: название, язык, адрес RSS.

**`crawler.py`** — сердце сбора. Для скорости разбито на два этапа:
1. **Параллельное скачивание** (`ThreadPoolExecutor`, до 5 источников
   одновременно) — только сеть, без обращения к базе или LLM, с
   тайм-аутом 15 сек на источник. Раньше зависший источник мог
   заблокировать весь сбор без предела по времени — это была реальная
   причина падений бота.
2. **Последовательная обработка** каждого фида — тут уже идёт
   дедупликация по ссылке, перевод (если язык не ru/en) и словарное
   тегирование. Последовательно специально: локальная LLM физически не
   рассчитана на несколько одновременных запросов.

Функции модуля:
- `collect_all()` — сбор новых статей
- `translate_existing_articles()` — перевод статей, которые ещё не на
  RU/EN, включая повторные попытки для тех, что не удалось перевести
  раньше (см. раздел про баг перевода ниже)
- `llm_tag_untagged()` — LLM-разметка того, что не взял словарь
- `compute_all_digests()` — пересчёт саммари по темам, но **только для
  тегов, у которых появилась новая статья** с прошлого пересчёта (иначе
  впустую тратился бы вызов LLM на неизменившиеся темы)
- `retag_all()` — полный пересчёт словарных тегов по всей базе;
  **не входит в автоматический цикл**, только ручной запуск (когда
  меняется `tags.py`), потому что новые статьи и так тегируются на лету
- `run_full_pipeline()` — обёртка над первыми четырьмя, вызывается
  автоматически раз в сутки

### Классификация (тегирование)

**`tags.py`** — встроенная таксономия: ~44 тега (`"5G": ["5g",
"пятого поколения", ...]`), от базовых технологий до конкретных
компаний-конкурентов (вендоры, операторы, спутниковые игроки,
чипмейкеры) и актуальных трендов отрасли (5G-Advanced, AI-RAN, RedCap,
Network APIs, гипермасштабируемые облака).

**`tagger.py`** — сопоставление текста с тегами по границам слов (не
любая подстрока — так «5g» не сработает внутри «5gb»), с нормализацией
типографских символов (например, «Wi‑Fi» с нестандартным дефисом всё
равно совпадёт с «wi-fi»). Поддерживает «корни слов» через `*`
(«коаксиал*» ловит и «коаксиальный», и «коаксиальном»). Подключает не
только встроенные теги из `tags.py`, но и пользовательские — из базы,
динамически при каждом вызове.

**Пользовательские теги**: диалог `/addtag` → LLM сама генерирует 4-8
ключевых слов на русском и английском. Хранятся отдельно от встроенных
— в таблице `custom_tags`, чтобы не трогать код (`tags.py`) на каждое
пользовательское добавление. Применяются автоматически к новым
статьям; на уже собранные — после ручного `retag_all()`.

**`llm_client.py`** — вся работа с Ollama:
- `llm_tag_article()` — теги для статьи строго из закрытого списка
  (встроенные + пользовательские), результат дополнительно
  фильтруется — модель физически не может "придумать" несуществующий тег
- `llm_match_query()` — понимание запроса на естественном языке,
  подбор ближайшего существующего тега
- `llm_translate_to_english()` — перевод. Возвращает `None` при
  неудаче, а НЕ исходный текст — это принципиально важный фикс: раньше
  при сбое перевода (например, Ollama временно недоступна) функция
  возвращала оригинальный текст как будто это и есть перевод, и статья
  ошибочно помечалась как "переведено". Китайский текст в результате
  навсегда оставался в базе под видом английского, и никакой повторный
  проход его больше не трогал. Теперь сбой явно виден вызывающему коду,
  статья остаётся в очереди на повтор
- `llm_summarize_topic()` — саммари по теме на основе последних статей
- `llm_generate_keywords()` — ключевые слова для нового пользовательского тега

Каждая функция умеет разбирать ответ модели даже если та обернула
JSON-массив в объект (`{"tags": [...]}` вместо голого массива) —
частое поведение моделей даже в строгом JSON-режиме.

### Хранилище

**`db.py`** — вся работа с SQLite (`articles.db`). Таблицы:
- `articles` — статьи: заголовок, источник, ссылка, даты, язык, аннотация
- `article_tags` — связь статья↔тег
- `tag_digests` — кэш саммари по темам (обновляется раз в сутки, только
  для тегов с новыми статьями — см. известный нюанс ниже)
- `custom_tags` — пользовательские теги с ключевыми словами

`save_tags()` — единая точка сохранения тегов, с валидацией: тег
физически не попадёт в базу, если его нет ни во встроенной таксономии,
ни среди пользовательских — защита от повторения истории с "мусорными"
тегами из старой версии (когда сырые RSS-категории засоряли базу).

`get_trending_tags()` — расчёт трендов с защитой от искажения молодой
базой: сравнение "к предыдущему периоду" требует минимум 14 дней
истории. Если бот работает меньше — честно переключается на простой
рейтинг активности за неделю вместо ложного "всё выросло на 100500%"
(баг более ранней версии: сравнение шло с периодом, который физически
не мог существовать, потому что бот тогда ещё не собирал статьи).

### Обработка запросов

**`hashtag_search.py`** — формирует ответ на тему:
1. Точное совпадение по имени тега или синониму (включая пользовательские)
2. Если не нашли — LLM пытается понять смысл запроса
3. Ответ: краткое кэшированное саммари темы + до 5 свежих статей
   (кликабельные ссылки) + динамика упоминаемости за неделю/месяц/квартал
4. Если тема не найдена вообще нигде — бот сам предлагает добавить тег
   через диалоговый `/addtag`

## 4. Технологический стек

| Компонент | Инструмент |
|---|---|
| Язык | Python 3 |
| Telegram-бот | `python-telegram-bot` |
| Сбор RSS | `feedparser` + `requests` (с тайм-аутами) |
| Параллелизация сети | `concurrent.futures.ThreadPoolExecutor` |
| База данных | SQLite |
| LLM | Ollama + `qwen2.5:7b-instruct`, локально на видеокарте |
| Планирование задач | встроенный `JobQueue` |

## 5. Как обрабатывается один запрос пользователя — по шагам

1. Пользователь пишет `#5G` или «что там с китайскими операторами»
2. Если начинается с `#` — сначала ищем точное совпадение с тегом или
   его синонимом (мгновенно, без LLM)
3. Не нашли — просим LLM подобрать ближайший из существующих тегов
   (за несколько секунд); LLM не может ответить ничем, кроме реального
   тега из списка или `none`
4. Не помогла и LLM — предлагаем пользователю самому добавить тег
   через `/addtag`
5. Тег найден — собираем ответ из базы: кэшированное саммари, до 5
   статей, динамика. Ничего не пересчитывается заново «на лету» из
   соображений скорости, кроме самого списка статей и динамики (лёгкие
   SQL-запросы) — тяжёлое (саммари) уже готово из ночного цикла

## 6. Известные компромиссы и нюансы (сознательные упрощения прототипа)

- Динамика считается по **дате сбора ботом**, а не по дате публикации
  на сайте источника — разные источники присылают дату в разных
  форматах, надёжный парсинг всех вариантов не стал приоритетом
- Тренды первые 2 недели работы бота показывают активность, а не рост
  — это осознанное поведение, не баг (см. `get_trending_tags`)
- Кэш дайджеста обновляется только при появлении НОВОЙ статьи по теме —
  если старая статья задним числом меняется (например, дозревает
  перевод), это само по себе не триггерит пересчёт дайджеста. На случай
  разовых сбоев есть отдельный скрипт `check_digests.py`, который ищет
  и сбрасывает "протухшие" дайджесты вручную
- LLM-задачи (перевод, теги, дайджесты) выполняются последовательно, не
  параллельно — ограничение локальной модели на одной видеокарте
